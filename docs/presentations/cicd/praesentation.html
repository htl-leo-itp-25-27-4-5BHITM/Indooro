Vom Commit bis in die LeoCloud: wie unsere Pipeline wirklich funktioniert

Stand 27.11.2026 · alle Zahlen aus Repo und GitHub

Wir zeigen in etwa elf Minuten, wie Code bei Indooro von einem Commit bis in die LeoCloud kommt. Zuerst die drei Begriffe und ein paar Wörter, dann unsere echte Pipeline mit den Tests und was wir über GitHub-Actions-Minuten gelernt haben, dann die Rolle von Claude Code und ein echtes Beispiel. Am Ende sagen wir ehrlich, was gut läuft und was fehlt.

Begriffe, erklärt wie bei der Post

Drei Stufen: Wie viel läuft automatisch?

Continuous Integration

Inhalt prüfen: Jede Änderung wird sofort automatisch gebaut und getestet.

„Passt alles zusammen?“

Continuous Delivery

Paket packen: Nach grünen Tests liegt ein fertiges Programm im Lager. Ein Mensch schickt es ab.

„Könnten wir jetzt liefern?“

Continuous Deployment

Automatisch zustellen: Jede grüne Änderung geht ohne Mensch direkt live.

„Geht es von selbst live?“

Der einzige Unterschied zwischen Delivery und Deployment: Wer drückt auf „Abschicken“?

Vergleich mit der Post. CI heißt: Bevor etwas ins Paket kommt, wird es geprüft. Das passiert bei jeder Änderung automatisch. Continuous Delivery heißt: Das Paket ist fertig gepackt und liegt im Lager. Jemand muss es noch abschicken. Continuous Deployment heißt: Die Post holt jedes fertige Paket sofort automatisch ab. Merksatz: Delivery und Deployment unterscheiden sich nur darin, ob ein Mensch auf Abschicken drückt.

Wo steht Indooro?

Prüfen und Packen: automatisch. Abschicken: von Hand.

Continuous Integration

Ja

Jeder Pull Request startet automatisch die passenden Tests.

Continuous Delivery

Ja

Nach jedem Merge entsteht automatisch ein fertiges Docker-Image.

Continuous Deployment

Nein

Live geht es erst, wenn Erik es in der LeoCloud einspielt. Mit Absicht.

Ehrlich sagen: Wir haben kein Continuous Deployment, und das ist Absicht. Vor jedem Live-Gang machen wir ein Backup der Datenbank, wir spielen nichts ein, während gerade im Markt getestet wird, und danach prüfen wir, ob alles läuft. Außerdem hat nur Erik Zugang zur LeoCloud.

Sechs Wörter, dann versteht man alles

Kurz erklärt

Branch

Eigene Kopie des Codes. Man arbeitet daran, ohne main zu stören.

Pull Request

Antrag: „Bitte meine Änderung in main übernehmen.“

GitHub Actions

Roboter von GitHub. Startet bei jedem Pull Request die Tests.

Docker-Image

Fertig verpacktes Programm. Läuft auf jedem Server gleich.

GHCR

Lager für unsere Images bei GitHub (GitHub Container Registry).

LeoCloud

Server der HTL Leonding (Kubernetes). Dort läuft Indooro live.

Diese sechs Wörter kommen in jeder weiteren Folie vor. main ist der Hauptzweig, also die offizielle Version des Codes. Ein Branch ist eine Arbeitskopie. Mit einem Pull Request fragt man, ob die Änderung in main darf. GitHub Actions ist der Roboter, der dann automatisch testet. Am Ende entsteht ein Docker-Image, also das fertig verpackte Programm, das im Lager GHCR liegt. Die LeoCloud ist der Kubernetes-Cluster der Schule, auf dem unser Server läuft.

Continuous Integration

Continuous Delivery

Von Hand

Schritt 1 bis 4 laufen von selbst. Nur der gestrichelte Pfeil braucht einen Menschen.

Das ist das wichtigste Bild, am besten von links nach rechts durchgehen. Eins: Jemand schreibt Code auf einem eigenen Branch, entweder wir oder Claude Code. Zwei: Ein Pull Request auf GitHub. Drei: GitHub Actions startet automatisch alle Tests. Vier: Wenn alles grün ist und gemergt wurde, baut GitHub ein Docker-Image und legt es in GHCR ab. Fünf: Erik holt dieses Image mit einem Befehl in die LeoCloud. Dieser letzte Pfeil ist gestrichelt, weil er von Hand passiert.

Was wir gelernt haben

Warum die Tests so viele Minuten brauchten

~1.600

von 2.000 GitHub-Actions-Minuten im November verbraucht

×10

Eine Mac-Minute zählt so viel wie zehn Linux-Minuten

31 min

dauert ein iOS-Testlauf auf dem Mac

  • Bis zu 9 KI-Agenten arbeiten gleichzeitig, jeder pusht auf seinen eigenen Pull Request
  • Jeder Push startete alle Tests, auch wenn sich nur Doku oder eine Webseite änderte
  • Alte Läufe liefen weiter, obwohl schon ein neuerer Push da war
  • Entwürfe und wackelige Tests (Zeitüberschreitung, Maven 429) kosteten Extra-Läufe
Das haben wir im November gemerkt: Unsere Organisation hat 2.000 GitHub-Actions-Minuten im Monat, und wir lagen bei ungefähr 1.600. Der größte Kostentreiber ist der Mac: GitHub rechnet eine macOS-Minute zehnmal so hoch wie eine Linux-Minute, und unser iOS-Lauf hat zuletzt 31 Minuten gedauert. Dazu kommt unsere Arbeitsweise mit vielen KI-Agenten gleichzeitig: Jeder Agent hat seinen eigenen Branch und Pull Request, und jeder Push hat bisher die komplette Pipeline gestartet. Die CI-Kosten wachsen also mit der Zahl der Pushes, nicht mit der Zahl der Menschen.

Die Lösung (PR #246)

Nur testen, was sich geändert hat

1

Ein kleiner Job schaut zuerst, welche Ordner sich geändert haben. Nur die passenden Tests starten.

2

Neuer Push auf denselben Pull Request? Der alte Lauf wird abgebrochen.

3

Entwürfe überspringen die schweren Tests. Sie starten bei „Ready for review“.

4

Der Mac läuft nur, wenn sich iOS-Code ändert. Linux geht dort nicht.

5

Wackelige Tests: nur bei bekannten Fehlern und nur einmal neu starten.

6

Nach dem Merge auf main läuft weiterhin alles. Das Image entsteht wie vorher.

Weiterhin automatisch: Jeder Pull Request wird geprüft, nur gezielter. Merke: Bei vielen parallelen Agenten kostet jeder Push.

Die drei großen Hebel sind billig: Pfadfilter, alte Läufe abbrechen und Entwürfe überspringen. Technisch: Der Job changes nutzt dorny/paths-filter und setzt pro Bereich ein Ja oder Nein, zum Beispiel backend, admin-ui oder web-quality. Der API-Vertrag läuft trotzdem bei jedem Pull Request, weil er billig ist und viel schützt. Warum iOS auf dem Mac bleibt: Unsere Swift-Pakete nutzen Apple-Bibliotheken wie simd, CoreGraphics, CryptoKit und Combine, die es unter Linux nicht gibt. Neu starten macht unser Werkzeug pr-wait: Es startet einen roten Job genau einmal neu, und nur wenn das Log zu einem bekannten Störfall passt, etwa Maven 429 oder ein Mac-Runner, der nicht startet. Echte Fehler bleiben rot. Gemergt wurde das am 27.11.2026.

Das ist der Teil, den wir bewusst von Hand machen. Erik macht das mit seinem LeoCloud-Zugang, manchmal lässt er Claude Code die Befehle ausführen, aber nur auf ausdrückliche Anweisung. Der wichtigste Befehl ist kubectl set image: Er sagt Kubernetes, welche Version laufen soll, und Kubernetes holt sie selbst aus dem Lager. Smoke-Check heißt: ein kurzer Test, ob die wichtigsten Seiten antworten, wie Rauch, der zeigt, ob etwas brennt. Jedes Release ist in docs/pilot-readiness/releases protokolliert.

Claude Code ist nicht Teil von GitHub Actions, es sitzt davor und schreibt Code. Zuerst wird ein Plan in openspec geschrieben. Dann arbeiten mehrere Claude-Sessions gleichzeitig, jede in ihrer eigenen Arbeitskopie, einem sogenannten git worktree, auf einem eigenen Branch. Jede öffnet einen Pull Request, und dort laufen genau dieselben Tests wie bei uns. Ein roter Test bleibt rot, egal wer den Code geschrieben hat. Die Zahlen kommen aus git log und der PR-Liste auf GitHub: 125 PR-Texte enthalten den Vermerk Generated with Claude Code.

Hier PR 241 im Browser öffnen. Die Geschichte: Unser Code war in Ordnung, aber Maven Central, der Server, von dem Java-Bibliotheken geladen werden, hat den GitHub-Roboter wegen zu vieler Anfragen abgewiesen. Die Pipeline wurde rot und nichts kaputtes ging raus. Claude Code hat die Lösung als Pull Request gebaut: warten und neu versuchen. Erst als alle fünf Checks grün waren, wurde gemergt. Zum Zeigen im Terminal: gh run list --limit 10.

Bilanz

Was gut läuft, was fehlt

Gut

  • Über 3.200 automatische Tests, pro PR nur die passenden
  • Echter Browser und echte Datenbank in den Tests
  • Jede Version eindeutig benannt, Rückweg dokumentiert
  • Code von Claude geht durch dieselben Tests

Fehlt

  • Live gehen nur von Hand, nur mit Eriks Zugang
  • main ist nicht gesperrt: Mergen ginge auch bei roten Tests
  • Kein zweiter Mensch prüft den Pull Request auf GitHub
  • iOS wird nur getestet, nicht verteilt; Android hat noch keinen Code
Ehrlich bleiben. Fakten aus GitHub: main hat keinen Branch-Schutz. Dass wir nur mit grünen Tests mergen, ist eine Teamregel, technisch erzwungen ist es nicht. Keiner der 133 gemergten Pull Requests hat ein formales Review auf GitHub, geprüft wird in der Claude-Session und vom Menschen, der mergt. Nächste Schritte wären: main sperren, sodass rote Tests den Merge blockieren, und ein Deploy-Knopf in GitHub mit Freigabe, falls die LeoCloud das erlaubt.
