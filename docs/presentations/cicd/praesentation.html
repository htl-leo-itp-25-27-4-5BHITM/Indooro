CI/CD bei Indooro

Vom Commit bis in die LeoCloud: wie unsere Pipeline wirklich funktioniert

Stand 27.11.2026 · alle Zahlen aus Repo und GitHub

Wir zeigen in etwa acht Minuten, wie Code bei Indooro von einem Commit bis in die LeoCloud kommt. Zuerst die drei Begriffe, dann unsere echte Pipeline, dann die Rolle von Claude Code und ein Live-Beispiel. Am Ende sagen wir ehrlich, was gut läuft und was fehlt.

Begriffe

Drei Stufen, eine Frage: Wie weit läuft es automatisch?

Continuous Integration

Jede Änderung wird früh in den Hauptzweig integriert. Ein Server baut und testet sie automatisch.

Continuous Delivery

Nach grüner CI entsteht automatisch ein auslieferbares Paket. Ein Mensch entscheidet, wann es live geht.

Continuous Deployment

Jede grüne Änderung geht ohne menschlichen Schritt automatisch in Produktion.

CI = bauen + testen · Delivery = Paket liegt bereit · Deployment = Paket geht automatisch live

Der Unterschied liegt nur im letzten Schritt. Bei Continuous Delivery liegt das fertige Paket bereit und ein Mensch drückt auf den Knopf. Bei Continuous Deployment gibt es diesen Knopf nicht mehr. Bild: Paket gepackt und abholbereit gegen Paket wird automatisch zugestellt.

Wo steht Indooro?

CI und Delivery ja. Deployment bewusst manuell.

Continuous Integration

Ja

Jeder Pull Request nach main startet die Checks in .github/workflows/ci.yaml.

Continuous Delivery

Ja

Jeder Push auf main baut ein Docker-Image und legt es in GHCR ab, Tag = Commit-SHA.

Continuous Deployment

Nein

Kein Workflow deployt. Rollout per kubectl nach Runbook, mit Backup und Smoke-Check.

Ehrlich sagen: Wir haben kein Continuous Deployment. Das ist eine bewusste Entscheidung. Laut Release-Runbook gibt es vor jedem Rollout ein Backup, nie einen Rollout während einer Pilot-Sitzung im Markt, und danach einen Smoke-Check. Außerdem hat nur Erik Zugang zur LeoCloud.

Continuous Integration

Continuous Delivery

Manuell

Die LeoCloud zieht das Image aus GHCR. Kein Workflow hat Zugang zum Cluster.

Das ist das wichtigste Bild. Links bis GitHub Actions ist CI. Das fertige Image in der GitHub Container Registry ist Continuous Delivery. Der letzte Pfeil ist gestrichelt, weil er manuell ist. Wichtig: GitHub schiebt nichts in die LeoCloud. Kubernetes zieht das Image, sobald jemand mit kubectl den neuen Tag setzt.

Was bei jedem Pull Request läuft

Fünf Jobs in ci.yaml, dazu iOS auf macOS

backend-testubuntu-latest + OpenSearchAdmin-UI- und Showcase-Tests, mvn verify, Ops-Skripte

Außerdem: beacon-lab.yaml und field-tools.yaml, nur Tests, nur bei Änderungen in ihren Ordnern.

Ein Satz pro Job. contract prüft den API-Vertrag in openspec/specs/shared-api/openapi.yaml und erkennt Breaking Changes. backend-test startet einen echten OpenSearch als Service-Container und führt mvn verify ohne skipTests aus. Die zwei Browser-Jobs testen Admin-UI und Showcase in echtem Chromium. build-and-push wartet auf contract und backend-test. Bei einem PR baut er nur, beim Push auf main pusht er das Image. iOS läuft in einem eigenen Workflow auf einem Mac-Runner.

Tag = 7-stelliger Commit-SHA, dazu :latest. Im Cluster laufen nur SHA-Tags.

Einziges Secret der Pipeline: GITHUB_TOKEN, automatisch von GitHub.

Ein einziges Image enthält Backend, Admin-Oberfläche und Showcase. Deshalb braucht die LeoCloud keinen eigenen Web-Container. Der Tag ist der Commit-SHA, hier 8238b4c vom grünen Lauf am 25.11. So wissen wir genau, welcher Code läuft, und können gezielt zurückrollen. Die Pipeline braucht kein eigenes Secret: Das GITHUB_TOKEN reicht für den Login bei GHCR.

Claude Code ist kein Teil von GitHub Actions. Es sitzt davor. Eine Orchestrator-Session teilt die Arbeit, startet Sub-Sessions, jede in einem eigenen git worktree auf einem eigenen Branch. Die öffnen PRs gegen main, und dort laufen exakt dieselben Checks wie bei uns. Ein Agent kann einen roten Check nicht wegreden. Die Zahlen kommen aus git log und gh pr list.

Bilanz

Was gut läuft, was fehlt

Gut

  • Jeder PR: Vertrag, Backend mit echtem OpenSearch, zwei Browser-Suiten, iOS
  • Breaking Changes an der API werden automatisch erkannt
  • Fester SHA-Tag, Rollback und Backup dokumentiert
  • Claude-PRs durchlaufen dieselben Checks

Fehlt

  • Kein Continuous Deployment, Rollout nur mit Eriks Zugang
  • main ohne Branch-Schutz, keine GitHub-Reviews
  • Browsertests blockieren den Image-Build nicht
  • iOS nur Tests, kein TestFlight; Android ohne Pipeline
Ehrlich bleiben. Fakten aus GitHub: main hat keinen Branch-Schutz und keine Rulesets, grüne Checks sind also eine Teamregel, nicht erzwungen. Keiner der letzten 133 gemergten PRs hat ein formales GitHub-Review. build-and-push wartet nur auf contract und backend-test. Nächste Schritte wären Branch-Schutz mit Pflicht-Checks und ein Deploy-Workflow mit manueller Freigabe, falls die LeoCloud einen Zugang für CI erlaubt.
