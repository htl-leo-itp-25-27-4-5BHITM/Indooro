# Release 2026-10-16: Admin-Neubau (PR #105) – Rollout fehlgeschlagen, Rollback erfolgreich

## Ablauf

| Schritt | Ergebnis |
|---|---|
| DB-Backup | `~/indooro-backups/indooro-2026-10-16-before-admin.dump` (186.715 Byte), `pg_restore --list` erfolgreich |
| Produkt-Backup | `~/indooro-backups/products-2026-10-16.json`, 153 Produkte, gültiges JSON. Erster Abruf von `/api/products` lieferte einmalig HTTP 500, der Folgeversuch HTTP 200 |
| Rollback-Punkt | laufender Digest `sha256:ffdfb66b6b9c9c971290548d87e2f204139b2c4db41f4562f619bed493271e85` |
| Merge | PR #105 als Merge-Commit `39b5f9a` auf `main` |
| CI | Lauf `38886708287` grün, Images `:latest` und `:39b5f9a` gepusht |
| Rollout | `kubectl rollout restart deployment/indooro-backend` → `rollout status --timeout=300s` lief in den Timeout |
| Rollback | `kubectl set image` auf den alten Digest; Deployment 1/1 bereit, Pod nachweislich auf `ffdfb66…271e85` |
| Smoke nach Rollback | 4 Stores, 48 Layout-Elemente im geprüften Store, Produktsuche HTTP 200, `/admin/` und `/admin/next/` HTTP 302, 153 Produkte (vor und nach dem Versuch gleich) |

## Befund

Kubernetes-Events des neuen Pods (`indooro-backend-7b6f67675-*`):

- Mehrere Neustarts in etwa zwei Minuten, danach `Back-off restarting failed container`.
- `Startup probe failed: dial tcp …:8080: connect: connection refused`, später `failed startup probe, will be restarted`.
- Startup-Probe: TCP 8080, alle 5 s, `failureThreshold 24` (max. 120 s). Limits: CPU 500m, Memory 512Mi.

Die Container-Logs gingen beim Rollback verloren, die Ursache ist daher **nicht belegt**.

Lokale Reproduktion (2026-10-16):

- Jar aus `39b5f9a`.
- Gestartet mit `eclipse-temurin:25-jdk`, `--memory=512m --cpus=0.5`, leerem PostgreSQL 16 und OpenSearch 2.9, ohne Keycloak.
- Ergebnis: Start in 10 s, Flyway V1–V11, kein Absturz.

Der Fehler hängt also an der LeoCloud-Umgebung: echte Daten, echter Keycloak oder die Umgebungsvariablen des Deployments.

Der Merge enthält keine neuen Migrationen und keine Änderungen an Entities, `pom.xml` oder Dockerfile. In `application.properties` geändert:

- Security-Header (CSP, nosniff, Referrer-Policy, HSTS)
- `quarkus.oidc.roles.source=accesstoken`
- `token-state-manager.strategy=keep-all-tokens`; das Deployment überschreibt diesen Wert per Umgebungsvariable
- Admin-Permission jetzt auch für `/api/categories*`

## Aktueller Stand

- `main` enthält den Admin-Neubau, LeoCloud läuft weiter mit dem alten Image.
- Das Deployment ist auf den alten **Digest** festgelegt, nicht auf `:latest`. Neustarts oder neue CI-Builds ändern daher nichts, bis jemand das Image bewusst setzt.

## Nächster Schritt (Freigabe durch Erik nötig)

Echte Logs ohne Risiko holen: `:39b5f9a` als einzelnen Canary-Pod mit derselben Umgebung starten.

- Eigenes Label, daher kein Traffic vom Service.
- Keine Probes, `restartPolicy: Never`.
- Logs lesen, dann den Pod löschen.

Danach die Ursache beheben. Rollout erneut mit einem Image-Tag pro Commit, Backup und Smoke-Check.
